# Prospective writer and independent recovery — 2026-10-11

C6 changes the automated write boundary from caller-supplied game/team/prior snapshots to `refreshGame(gameId, { onlyIfMissing, deadlineMs })`. Cron, `run-daily.ts`, and `project_fatigue.ts` all use it. The pure `refreshDailyGames` abstraction remains for historical/replay tests; no database implementation of its snapshot/write port remains. Manual historical backfills remain separate and do not acquire this prospective guarantee.

The transaction uses READ COMMITTED. Its first data statement locks `games.id FOR UPDATE` and completes before the next statement reads the target, both teams, and both prior-game sets in one SQL snapshot. Result-derived inputs of unplayed priors are neutralized through the existing helper. The unchanged pure fatigue calculation runs inside the transaction; two fatigue rows and unresolved predictions are replaced atomically. Resolved predictions survive, and a conditional insert suppresses an open pick when a resolved pick exists. Gap mode checks both sides after the target lock. No schema or coefficients changed.

Eligibility requires scheduled status and a known future tip. Actual `clock_timestamp()` is checked after acquiring the lock (snapshot), before replacement, between write phases, and after the final write. Crossing tip or the deadline throws inside the transaction and rolls back. Lock and statement timeouts are at most 1.5 seconds. Each game also has a four-second deadline; cron carries a 55-second route deadline below its 60-second platform limit. PostgreSQL settings bound server statements/lock waits, not waiting for a connection in the application pool. The four-second deadline can be exceeded by the final bounded statement/rollback; it is not an exact wall-clock cancellation guarantee. Pool saturation/platform cancellation remains an unverified operational limit.

C1 runs its recovery scan after the score stage settles, including no unfinished score rows and ESPN failure. The current season's first known-future scheduled game per team is selected in tip order; targets must be today or tomorrow ET and have a prior stored FINAL in the existing 30-day model input window. Source-final writes are independent and remain committed even when fatigue refresh fails. Calendar neighbors use the ET date key rather than ±24 hours. Dates fetch independently: good-date finals remain when another feed fails. Public errors are fixed sanitized messages, with score/fatigue failure, skip, and deferred counts. Internal logs retain failed IDs and skipped/deferred details.

Targets are ordered by oldest fatigue computation (missing first), then tip and ID. Completed targets move behind older work on the next invocation; failed/skipped/deferred counts are not silently dropped. This is repeated reconciliation, not a durable outbox. Prior/source updates are not locked by the target lock: both sides are coherent at the fresh snapshot, and later source changes converge on a later run. The existing 08–21 UTC cron gap still prevents a universal pre-tip guarantee. Null-tip rows are excluded from the cron scan and reported as skips by daily/projection writers when selected.

Score writes now protect finals at commit time in both cron and `sync_scores_espn.ts`: a nonfinal update includes `current status != final` in the UPDATE predicate; a final input remains eligible to correct another final. The returned game IDs determine committed counts and write-time refusal counts. A stale source read cannot downgrade a final that another writer commits while it waits on the row. This does not establish source-version ordering between conflicting final corrections. Malformed cron scoreboard envelopes (missing/non-array `events`) fail closed with 502 while independent recovery still runs; a valid empty events array remains a legal feed result.
